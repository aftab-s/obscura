# Exercise 3 — Continuous Integration

## Goal

Make every push automatically test the application, build the Docker image, and push it to Docker Hub.

The workflow lives in:

`.github/workflows/ci.yml`

### Inspect it

Look for:

1. Trigger — what events start the pipeline?
2. Runner — where does it execute?
3. Python setup — which version?
4. Dependency installation
5. Tests — what runs?
6. Docker Hub login — how are credentials managed?
7. Docker build and push — how is the image tagged?

### Set up Docker Hub secrets

Before the pipeline can push images, you need to add two secrets in your GitHub repository:

1. Go to **GitHub → Settings → Secrets and variables → Actions**
2. Add `DOCKERHUB_USERNAME` — your Docker Hub username
3. Add `DOCKERHUB_TOKEN` — a Docker Hub [personal access token](https://docs.docker.com/security/for-developers/access-tokens/)

### Trigger the pipeline

```bash
git add .
git commit -m "Add Docker support"
git push
```

Then open:

**GitHub → Actions**

Watch for two jobs:

1. **test** — installs dependencies and runs `pytest`
2. **docker** — builds the image and pushes it to Docker Hub (only runs after tests pass)

Once the pipeline succeeds, verify your image on Docker Hub:

```
https://hub.docker.com/r/<your-username>/grade-predictor
```

### Challenge

Change the application and intentionally make one test fail.

Push the change.

Observe the failed pipeline — notice that the Docker push does **not** run when tests fail.

Fix it and push again.

## Discussion

CI is not "GitHub Actions".

CI is the practice of automatically validating changes whenever code changes.

Tools can change. The principle remains.

The pipeline now goes beyond testing — it produces a deployable artifact (a Docker image on Docker Hub) on every successful push.
